# ADR 0004: 工作流优先的智能体交互

日期: 2026-08-31
状态: 已接受

MonkeyFence 的智能体体验以项目工作流为中心:用户在项目工作流里定义可重复运行的 DAG,直接点击运行;系统在后台自动创建 Task、冻结 Pipeline Revision 并启动调度。Task 状态机继续作为内部可靠性机制存在,负责调度、崩溃恢复、结算令牌与幂等,但不再主导用户导航;用户看到的顶层结构只有"工作流"和"运行",需要人工介入时通过运行级提醒(需要你)召回。

项目工作流不等于任务本地工作流草稿。任务本地草稿依附于某个 Task,是编排过程中的一次性输入;项目工作流是项目内的一级对象,跨运行和重启保留,与任何 Task 都没有从属关系。把两者混为一谈会让"先建 Task 再编排"成为强制路径,而单次编排草稿也无法承担"可重复运行的项目资产"这一职责。因此项目工作流拥有独立存储与独立生命周期,任务本地草稿原样保留以兼容既有流程。

同理,全局工作流模板是显式的跨项目复用入口:从模板创建项目工作流时复制模板当前版本,之后两者互不联动;项目工作流不会自动晋升为全局模板。单 Agent 场景被建模为单节点项目工作流,而不是第二套执行路径,保证所有运行共享同一套调度、结算与恢复语义。

不删除 Task 状态机、Ad-hoc 会话、Orchestrator、Settlement 和插件 pin 语义。这些机制继续按 ADR 0001/0002/0003 运行;本决策只改变它们之上面向用户的组织方式。需要你是运行级投影:进程退出、终端空闲或 `done` 上报都不能自动等同于成功结算,这些情况一律进入需要你,由用户显式解除;仅因上游失败而被阻塞的后代节点不单独计数,一个运行最多贡献一个提醒。
